## 0. Headline findings (read these first)

1. **Tenancy model is `Client` (tenant) -> `CloudAccount` (connection to one AWS account).** `TenantFilter` currently forces `TenantContext` to the constant `"system"` (single-tenant DB mode). Real isolation is by `ClientUserDetails.getClientId()` plus `CloudAccountAccessService`. Observability must key every row and every query on `client_id` + `cloud_account_id` (the PK), never on the 12-digit `aws_account_id` (an AWS account can be connected more than once; the inventory code documents the bug this caused).
2. **The existing agent is a Kubernetes-oriented JSON pusher on a 5-minute cadence** (collectors: trivy, kubescape, opencost, karpenter, k8s resources, prometheus, DB, disk). It has no host metrics, no log tailing that is not wired to a third-party backend, and no Windows build. Telemetry-grade collection must be a separate process. The agent's *identity, install, auth and distribution* machinery is what we reuse (see section 6 and the decision in `01-research-report.md`).
3. **Auth gotcha for machine callers:** `SecurityConfig.impersonationJwtFilterChain` (`@Order(1)`) claims every request that carries an `Authorization` header except `/api/llm-proxy/**` and `/api/v1/agent/**`. A new agent endpoint under `/api/obs/v1/agent/**` that uses `Authorization: Bearer` would be captured by that chain and rejected. Phase design must either (a) add `/api/obs/v1/agent/` to the exclusion list in that `securityMatcher`, or (b) use a dedicated header (recommended: `X-XamOps-Ingest-Token`). Same for the permitAll list in the second chain.
4. **The shared global agent key is baked into the legacy install script** (`xamops-agent/scripts/disk_agent_install.sh` contains a hard-coded global `XAMOPS_API_KEY`). Observability must never use or copy it. Account-scoped keys exist (`AgentApiKeyService`) and are the floor; Obs 1.0 should use *per-host rotating ingestion tokens* stored hashed.
5. **The readonly connection role cannot install anything.** `cloudformation/xamops-readonly-role.yml` attaches AWS-managed `ReadOnlyAccess` (so `ec2:Describe*`, `ssm:Describe*`, `s3:ListAllMyBuckets`, `s3:GetBucketLocation` etc. work) but has no `ssm:SendCommand`, no `s3:PutObject` on customer buckets, no `iam:*` role creation. Discovery, pre-flight and bucket listing work today; one-click install and BYO-S3 writes require a **new, opt-in, least-privilege nested stack** (pattern in section 7).
6. **Live tail must not use the STOMP broker.** `WebSocketConfig` uses the in-memory simple broker with `/topic` broadcast and no tenant filter (its own comment says so). Log tail must be SSE or a dedicated authenticated WebSocket handler (pattern: `CloudShellWebSocketConfig`), proxied through nginx with long read timeouts (`api-gateway/nginx-prod.conf` has no `/api/obs/` block yet).
7. **A design-rule test guards parts of the frontend** (`FE/test/designRules.test.ts`): no gradients, no emoji, no Font Awesome (in guarded paths), no raw hex/rgb outside token files, status never by colour alone. Guarded paths are an explicit allow-list (`GUARDED_PATHS`); new `features/observability-v1/` is not in it today, but Obs 1.0 should adopt the same rules and be added to the list deliberately.

## 7. CloudFormation role patterns

Files under `ROOT/cloudformation/` (verified): `xamops-readonly-role.yml`, `xamops-readonly-role-uat.yml`, `xamops-readonly-role-local.yml`, `xamops-readwrite-role*.yml`, `xamops-stack-updater.yml`, `xamops-upgrade.yml`, `xamops-cur-export-nested.yaml`, `xamops-cur-report.yml`, `xamops-inventory-engine.yaml`, `xamops-inventory-events-nested.yaml`, `xamops-deployer-policy.json`, `xamops-mpa-cur-role.yml`.

Conventions to copy into the new Obs template (new file, e.g. `cloudformation/xamops-observability-v1-*.yaml`; naming left to the design phase):

- **Trust:** role assumed by `arn:aws:iam::${XamOpsAccountId}:role/${XamOpsPrincipalRoleName}` with `Condition: StringEquals: sts:ExternalId: !Ref ExternalId` (readonly role lines ~181-193). `XamOpsAccountId` has `AllowedPattern '^\d{12}$'`, `ExternalId` has `MinLength: 10`.
- **Least-privilege with scoped resources:** the `XamOpsCurStackManage` policy (readonly role ~lines 598-650) grants CreateStack/UpdateStack only on `stack/XamOps-CUR-*/*` and S3 bucket provisioning only on `arn:aws:s3:::xamops-cur-*` and `.../*`; actions with no resource-level ARNs (`s3:ListAllMyBuckets`) carry a comment explaining why `Resource: '*'` is intentional. Copy this style: **bucket provisioning limited to `xamops-logs-*`**, stack actions limited to `XamOps-Obs-*`.
- **Nested stack for optional capability:** `xamops-cur-export-nested.yaml` creates a *dedicated* bucket (rationale in its header: owning the bucket end-to-end keeps scope tight and auditable). Obs "XamOps creates a dedicated bucket" mode should mirror this; "bring your own bucket" mode instead emits a *bucket policy/role snippet* for the customer to apply.
- **`iam:PassRole` discipline:** `xamops-readonly-role.yml` ~lines 966-1080 documents that XamOps holds change-set actions and `iam:PassRole` on a single deployer role and never `iam:CreateRole`. The Obs install stack (instance profile + SSM association) must go through the same deployer-role approach.
- **Callback:** `XamOpsEventBusArn` / `XamOpsCallbackUrl` parameters notify XamOps when a stack completes (`POST /api/xamops/account-manager/eventbridge-callback`, public). Obs can reuse the EventBridge bus for "stack ready" events but should add its own signed callback for "agent first data".
- **Gap to close:** neither connection role has `ssm:SendCommand`, `ssm:CreateAssociation`, `iam:CreateInstanceProfile`, `s3:PutObject` on customer log buckets, `s3:PutBucketLifecycleConfiguration` outside `xamops-cur-*`. All of these belong in the new opt-in stack and must be shown in the UI as a policy preview before the customer approves.
